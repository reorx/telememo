# 消息的形态、入库与展示

> 读者：刚接手 telememo，或者准备改动入库、同步、展示逻辑的人。
> 回答：一条 Telegram 消息在 telememo 里会变成哪几种形态，怎样入库并保持更新，最后怎样还原成用户在 Telegram 里看到的样子。

## 三种形态

| | Telegram 原始消息 | 存储记录 | 展示消息 |
|---|---|---|---|
| 视角 | Telegram API | 数据库里的一行 | 用户在 Telegram 里看到的一条 |
| 相册 | 每张图 / 每段视频各一条，共享同一个分组 id | 各占一行 | 合并成一条，带媒体列表 |
| 转发来源、链接预览 | 有 | 有，入库时提取 | 有 |
| 例：两个相册（4 张 + 2 张）加两条文字 | 8 条 | 8 行 | 4 条 |

存储层和 API 保持一对一，是为了让增量同步和编辑更新都能按消息 id 直接对应到行；「合并相册」只在展示时做，是对若干行的纯计算，不改动存储。

## 入库时保存什么

- 正文、时间、发送者、浏览数 / 转发数 / 回复数、编辑时间。
- 媒体只保存类型和像素宽高，**不下载文件**。嵌入方需要图片或视频时，按消息 id 向 Telegram 现取现传，不落盘。
- 链接预览只保存已经完整解析的那种（标题、描述、站点名等）；预览图不保存，只记录「有没有图」。
- 转发来源：来源频道或用户的 id 与名字、原消息 id、原始时间、署名。

### 转发来源的名字从哪来

按顺序取三个来源，取到为止：

1. 随消息一起返回的频道 / 用户信息，不需要额外请求。
2. 本地的名字缓存（id → 名字，持久化在一个 JSON 文件里）。
3. 向 Telegram 查询，并把结果写进缓存。

来源被隐藏的转发只有对方的显示名，没有 id。

第 3 步只在历史回填时使用。实时订阅只用前两步：实时处理里没有限流重试，一次查询被限流就会卡住整个事件循环；回填有限流退避，查到的名字进了缓存，之后的实时消息自然能用上。

命令行这条路径不带名字缓存，只有第 1 步。

## 相册的合并规则

- 组内 id 最小的那条作为主消息，消息 id、时间、发送者、转发来源都取它的。
- 正文取组内带文字的那条（通常是最后一条）。
- 浏览数、转发数取组内最大值，回复数取总和；任意一条被编辑过，整条就算编辑过。

回复数可能挂在组内任意一条上，不一定是带文字的那条。取评论时要先在组内找到带回复数的那条；频道关联的讨论组里，对应的那组消息也是同样的情况。

## 同步

命令行的 `sync` 有三种模式：

| 模式 | 何时 | 做什么 | 推进同步水位 |
|---|---|---|---|
| 增量 | 默认 | 取比上次水位更新的消息 | 是 |
| 刷新 | 增量没取到新消息 | 重新取最近 N 条（默认 100），用来捕获编辑 | 否 |
| 全量 `--full` | 手动 | 从头取全部，并无条件覆盖已有行的所有数据列 | 是 |

已存在的行只有在**编辑时间变了**才会重写。全量模式跳过这个判断，这是给旧数据库回填后来新增的列（链接预览、转发来源等）的唯一办法——数据库打开时会自动补上缺的列，但列里的值要靠一次全量同步填进去。

评论：频道必须关联了讨论组才有评论。只有新消息、或回复数和库里不一样的消息才会去取评论；评论本身同样按编辑时间决定是否重写。

`dump-messages` 和 `dump-comments` 是一次性导出，不记录同步水位；日常使用 `sync`。`dump-messages` 遇到已存在的消息时和全量同步一样无条件覆盖所有数据列，不看编辑时间。

## 嵌入到其他应用时

嵌入方（目前是 condenser）不走命令行那套，而是用一个长期运行的服务对象：

- **历史回填**：从新到旧取消息，到指定天数 / 日期或条数上限为止；也可以从一条已知消息继续往更早翻页。只有从最新一条开始的回填才推进同步水位，往回翻历史不会把水位拉低。
- **实时订阅**：新消息和编辑都会入库，并以展示消息的形式回调给嵌入方；编辑会再次回调，方便下游重新处理。
- **单库**：所有频道共用一个数据库，而命令行是一个频道一个库。表结构相同，消息本来就按「频道 + 消息 id」定位。
- **扩展列**：嵌入方可以在 telememo 的表上声明自己的列（比如「是否被过滤」）。telememo 的任何写入都不碰这些列，同步不会把它们清掉。
- **登录**：分步提交验证码和两步验证密码，登录态以字符串形式交给嵌入方自己保存和加密；不读取 telememo 的配置文件。

## 展示与搜索

查看器和嵌入方拿到的都是展示消息：从库里取出若干行，按上面的规则分组即可，转发来源直接读已保存的列。

搜索默认对正文做子串匹配，消息和评论分开搜，没有全文索引。消息搜索加上 `--include-webpage` 后，也会匹配已保存的链接预览标题、描述、站点名、作者与 URL，并在结果里显示预览内容。可以同时用 `--include-comments` 展示命中消息的评论，但不能与只搜评论的 `--comments` 同用。

链接预览搜索只使用本地已保存的 Telegram preview，不联网抓网页全文。旧记录的预览如果还未回填，需要全量同步；未解析的预览没有可搜索的内容。

## 相关代码

- 三种形态的定义：`telememo/types.py`（`MessageData`、`DisplayMessage`、`ForwardInfo`、`WebPagePreview`）
- 原始消息 → 存储记录、转发名字解析：`telememo/telegram.py`，名字缓存在 `telememo/entity_cache.py`
- 行 → 展示消息、转发来源提取：`telememo/utils.py`
- 表结构、自动补列、扩展列、按编辑时间判定的保存：`telememo/db.py`
- 命令行同步：`telememo/core.py`；嵌入用服务：`telememo/service.py`
- 测试：`tests/test_part_a.py`、`tests/test_smart_save_force.py`、`tests/test_forward_resolver.py`
- 查看原始消息长什么样：`scripts/debug_messages.py`
- 当前已知的偏差见 `kb/known-issues.md`
